The context
My current work centres on batch processing and data products. This project extends that experience into transactional and event-driven systems.

The ledger is the working environment. The focus is the reasoning behind its guarantees—and where those guarantees end.

01 / The investigation

What has to remain true
when things go wrong?

Through a mentorship ledger project, I explored a different set of operational problems from my day-to-day batch workloads. A transfer makes the questions concrete: can it happen twice, complete halfway, or disappear between services?

01 — ATOMICITY

All related writes, together.

Define a transaction boundary around postings, balances, the idempotency record, and the outbox event.

02 — IDEMPOTENCY

Repeat the request. Preserve the effect.

Recognise a retry without mistaking a different instruction for the original one.

03 — CONCURRENCY

Protect shared state.

Use database locks to coordinate requests that compete for the same records.

04 — RECOVERY

Carry work across failures.

Explore event delivery through an outbox and settlement recovery through Temporal.

How the implementation supports this behaviour
The server scopes the key to the authenticated client and hashes the operation and request body. Inside a PostgreSQL transaction, an advisory lock serialises requests for the same client and key.
  1. An unseen key runs the operation and saves its transaction reference.
  2. A known key with a matching hash loads the original transaction response.
  3. A known key with a different hash raises a conflict, returned as HTTP 409.
The outbox write sits on the new-transaction path, so replaying the existing transaction does not enqueue another event.

Where the guarantee stops
A fresh key represents a fresh instruction—even when its amount matches a previous request. The client must reuse the original key when retrying. This depends on retaining the idempotency record and using the same client scope; it is not a universal guarantee of exactly-once delivery across services.
This guided example fixes the client and accounts, and omits authentication, risk decisions, and real network timing to isolate idempotency. It does not measure database concurrency or backend performance.


03 / Engineering reflections
The useful part is
knowing the boundary.
A retry policy tells me when to try again. Idempotency determines whether trying again is safe.
From a job rerun to a request retry
Batch processing already raises questions about reprocessing and duplicate outputs. This investigation makes the boundary explicit at the request level: client identity, a stable key, a payload hash, and a committed result.
Local atomicity has a limit
PostgreSQL can commit related local writes together. Publishing to Kafka introduces another boundary. The outbox records the intent to publish inside the transaction; delivery and consumer duplicate handling remain separate responsibilities.
Next experiments to document
Competing transfers against one balance; a committed event waiting for its publisher; and a settlement that retries or releases a hold after bank rejection. Each deserves its own failure scenario and evidence.
